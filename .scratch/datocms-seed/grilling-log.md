# Grilling log: DatoCMS Seed (Core)

Running record of design decisions from the `/grill-with-docs` session started 2026-09-29. Terms are defined in `CONTEXT.md`; hard-to-reverse decisions are in `docs/adr/`. Deferred ideas are in `deferred.md`. Input for `/to-spec`.

Research: `docs/research/datocms-nextjs.md`, `docs/research/granular-cache-tags.md`, `docs/research/pa-ui-kit-obligations.md`, `docs/research/datocms-site-search.md`.
Client questionnaire (Italian, pending answers): `to-questionnaire-capodimonte-vincoli-pa.md`.

Scope rule: we are designing the **Core** of the Seed. Site-specific specs (Capodimonte) come later, from the shared client brief.

## Decided

### Foundation
- Stack: Next.js 16 App Router, React, Tailwind. Base: official DatoCMS **Next.js Starter Kit** (gql.tada typed queries with a fragment per component, `react-datocms` `<Image>`, draft mode via the Web Previews plugin).
- Hosting: **Netlify** (Capodimonte on Netlify Pro).
- Schema ownership: the Seed ships a small set of models (Starter Kit's plus what Core features need: Site settings, Page, Routing rule, Redirect, Menu, a few base Blocks). All other models are custom per Site. Every Routable model has an Editor-editable localized slug. Reference schema lives in a DatoCMS test project with versioned migrations in the repo.
- Reuse: Sites are copies of the Seed; the Core lives in its own folder, written to be extracted into an npm package later.
- Vocabulary: "Block" as in DatoCMS (not widget).
- Files in English; chat in Italian.

### Rendering & preview
- Draft mode for Editors (bypasses cache, always fresh). **No Visual Editing.**
- Public pages stay static (ISR-style); content always server-rendered.
- Unknown Block type: renders nothing in production, a visible "not implemented" placeholder in draft mode.

### Cache (ADR-0002)
- `fetch` with `force-cache`; Visitors get stale-while-revalidate (`revalidateTag(..., 'max')`).
- Two settings: invalidation mode `global` (default for a new Site) | `granular` (Capodimonte); index store behind an adapter, only **Turso** implemented now.
- Full revalidation on code deploy, deploy rollback, DatoCMS environment promotion.
- Netlify deploy contexts map to DatoCMS environments (production → primary, previews → sandbox); separate index per environment.

### Routing (ADR-0001)
- Single `[locale]/[[...slug]]` catch-all with a resolver; all Path segments come from DatoCMS.
- Always multilingual, translated URLs, every locale prefixed. Locales come from DatoCMS (`_site.locales`), first = default.
- `/` → 302 to browser language if available, else default locale.
- Missing translation → 404, excluded from sitemap/hreflang.
- Page Paths follow the native DatoCMS Page tree (hierarchical sorting).
- Other Routable models: Path = localized prefix + slug (e.g. `/it/articolo/<slug>`), via a **Routing rule** record per model (model, Main page, localized prefix; empty prefix → Main page's Path). Main page drives breadcrumbs, not the Path.
- Home page: any Page, chosen in **Site settings** (swappable, schedulable). The chosen Page's own Path 301s to the locale root.
- Pagination as Path suffix: `/it/articoli/pagina/2` (the word "pagina" is localized).
- Path collisions across models: serve the first match in a fixed model order.
- Redirects: manual Redirect model in DatoCMS (automatic ones deferred).
- 404 page content from a CMS Page designated in Site settings (static fallback); 500 page static, translated in code.

### Navigation
- Menus are independent records; Site settings assigns a Menu to each Menu zone (the same Menu may fill several). Seed zones: header, footer, top, mobile; Sites can add zones (new Site settings field + layout slot).
- Menu items as nested Blocks: internal link (any Routable model), external link, group, automatic "sub-pages of…". Max depth 3.

### SEO
- Metadata built from DatoCMS `_seoMetaTags` (with per-model fallback fields configured) + favicons; the Core adds canonical, hreflang, `og:image:alt`, `article:modified_time` (dropped by `toNextMetadata`). `noindex` from the native SEO field drives meta robots, sitemap and llms.txt exclusion.
- One exclusion rule: an excluded record/model gets meta robots `noindex`, is left out of the sitemap and out of llms.txt. The only allowed divergence: exclude from llms.txt only.
- Excluded models are declared in Site config (code). Sections are excluded on the Page tree: the existing `noindex` plus an "also exclude sub-pages" option on Page. No textual path patterns.
- Sitemap: sitemap index with one sitemap per model, auto-split past 50,000 URLs, `lastmod` from the record; no hreflang in the sitemap (only in `<head>`).
- robots.txt generated by the Core (DatoCMS doesn't manage it): rules from code (Seed defaults + Site rules) plus a free-text field in Site settings for extra rules, appended after the code rules. The Core drops (and logs) only lines that block DatoCMS's search crawler or are syntactically invalid; blocking the whole Site is allowed on purpose.
- Non-production (detected from the Netlify deploy context, not configurable): robots.txt disallows all crawlers except DatoCMS's search crawler, plus `X-Robots-Tag: noindex` on every response.
- AI crawlers: per-Site setting (allow all / block training crawlers / block all), default allow all. Never blocks DatoCMS's search crawler.
- Indexability principle (binding): all indexable content is server-rendered HTML; Client Components only for interactive parts, receiving data from the server; no indexable content loaded by the browser. Declared exceptions: Algolia search and other `noindex` content.
- Archive search filters live in the URL and results are server-rendered; the unfiltered page is static, filtered combinations are dynamic with a short cache. - Indexing of listing pages is the SEO configuration's call, not hard-coded: a Page holding a Listing or Archive search has its own SEO settings; its filtered combinations and subsequent pages (`/pagina/2`) inherit the Page's indexing setting. Neither is in the sitemap. Exceptions per URL pattern go in the robots.txt editor field (note: `Disallow` stops crawling, not indexing). Canonicals: subsequent pages self-canonical; filtered combinations canonical to the unfiltered page.
- Site search: the Page without a query follows its own SEO settings; results (`?q=…`) are always `noindex`, not overridable.
- Schema.org: Core provides WebSite, Organization, BreadcrumbList and a per-model JSON-LD hook; Site provides specific mappings (e.g. Museum, Event).
- llms.txt: index in the Core; per-page `.md` versions opt-in per Site.

### Search & listings
- **Listing** Block (Core): model, page size, order, one linked-record filter, pinned items. Sites add bespoke listings for complex filters.
- **Site search**: adapter; first implementation DatoCMS Site Search; Algolia later. Adapter exposes a capability flag for "narrow by model"; the UI adapts. The DatoCMS adapter reports it as unsupported (its API has no model/path filter; one-index-per-prefix rejected as fragile); narrowing comes with Algolia.
- Site search covers the whole Site: `noindex` and robots.txt address third-party crawlers only, so noindex content still appears in Site search results.
- Each Site search adapter declares whether it runs on the server or in the browser. DatoCMS Site Search runs server-side (the CMA search token never reaches the browser); Algolia runs in the browser only, with its search-only key, so search load goes to the third party, not the application. The search results page is `noindex` either way.
- Server-side search protection: search results are never cached; robots.txt disallows the search Path for third-party crawlers; a DatoCMS rate-limit response shows a friendly message, not a 500. Per-IP rate limiting is left to the platform (Netlify).
- Non-production robots.txt disallows every crawler except DatoCMS's search crawler, so Site search can be tested on previews that have a search index.
- The Core marks repeated layout parts (header, footer, Menus, breadcrumb, cookie banner) with `data-datocms-noindex`; Sites can mark more areas.
- **Archive search**: separate adapter; first implementation Content Delivery API filters; Algolia later for facet counts. Each model declares its filters in Site config (field, control type, label).

### Blocks, forms, consent, monitoring
- Core Block catalog, starting set: rich text, image, gallery, embedded video, call to action, text+image, FAQ, Listing, Site search, Archive search, contact form. Goal: cover every DatoCMS base Block; keep a tracked list of base Blocks not yet handled (research: `docs/research/datocms-base-blocks.md`).
- Base content coverage: the Core handles every native content shape (Structured Text nodes and marks, field types), enforced by a test. Blocks are tracked against a reference set (DatoCMS Schema Recipes + Starter Kit) in `block-coverage.md`, each marked handled / to do / not planned; it becomes a ticket.
- Video Block supports both uploaded video (Mux) and the external video field (YouTube/Vimeo); external video is gated by consent (preview + "load video" until accepted) and uses `youtube-nocookie` where possible.
- Contact form is in the Core; other forms (newsletter, bookings) are out for now. Fixed fields: name, email, subject, message, mandatory privacy consent with link to the privacy notice. Sent as email via SMTP through a delivery adapter; validated server-side, works without JS, accessible errors.
- Anti-spam/anti-bot is mandatory. Always-on baseline: honeypot field + minimum fill time. On top, a captcha behind an adapter: the Core implements reCAPTCHA, which loads only after consent (without consent the baseline alone applies). Proposal for the Capodimonte Site: ALTCHA (self-hosted proof-of-work, no cookies, accessible); paid EU alternative Friendly Captcha.
- Email details: SMTP credentials in Netlify env vars; recipient chosen in Site settings; Visitor's email as Reply-To, not sender; no confirmation copy to the Visitor (anti-relay); messages not stored; on SMTP failure the Visitor sees a clear error and the event is logged.
- Consent: Core defines a consent adapter (which cookie categories the Visitor accepted) and loads third-party scripts only after consent for their category; concrete tools (Iubenda, ministry banner, WAI) live in the Site.
- Monitoring: Core logs significant events (failed webhooks, cache fallback to global revalidation, unimplemented Blocks, missing Labels) through a logging adapter; default writes to Netlify logs, Sites may plug in e.g. Sentry.

### Block markup & extensibility
- Every Block rendered by the Core is wrapped in an element with speaking hooks: `class="dato-block dato-block--image-gallery"` (type from the model api_key, kebab-cased), a modifier class per Editor-chosen variant (`dato-block--image-gallery--grid`), `data-block-type="image_gallery"`, `data-block-id="<record id>"`. Prefix `dato-block` is the default, configurable per Site. Same scheme for Menus and Menu zones (`dato-menu dato-menu--header`). Structured Text text nodes get no classes (clean semantic HTML).
- No plugin/module system now. The Core stays open by construction (resolver accepts new Routable models, Block catalog accepts new Blocks, external services behind adapters); a module system is extracted when the Commerce Seed arrives.

### Out of the Core
- RSS feeds: out of the Core.
- Events and calendars: not in the Core; enabled per Site.
- Images: responsive and modern formats via react-datocms `<Image>`.

### Labels
- Static UI Labels in per-locale files in the Seed, extended/overridden per Site. Missing locale file → default-locale Labels + log warning; page `lang` stays the content's locale.

### UI & accessibility
- Seed is design-neutral with its own token layer; Designers Italia tokens live in the Capodimonte Site.
- Target WCAG 2.2 AA technically (first Site is PA: WCAG 2.1 AA legal minimum, accessibility declaration per project).

### Images & performance
- Alt text: a "decorative" flag on each Block that uses an image (not on the upload). Decorative → `alt=""`. Not decorative and alt missing → production renders `alt=""` and logs it; draft mode shows a visible warning to the Editor; axe tests fail. DatoCMS's native "required alt" validation is not used (it can't express decorative).
- Core Web Vitals, three levels: (1) Lighthouse CI in GitHub Actions against the Netlify deploy preview of each PR, on sample templates (home, Page, record, Listing), budgets LCP < 2.5 s, CLS < 0.1, TBT < 200 ms, client JS size cap; Seed defaults, tunable per Site; (2) field data via `web-vitals` sent to a Site endpoint (no cookies, no personal data) through the logging adapter or analytics; (3) design rules: priority hero image with declared sizes, local fonts via `next/font`, third-party scripts deferred and after consent, minimal Client Components.

### Testing
- Vitest (resolver, metadata/hreflang, cache invalidation, index adapter) + Playwright with axe on every template, against the DatoCMS test project; run in GitHub Actions CI on every PR.
